# AGENTS.md — Guide for AI Agents Working on MemberMocker

This document is written for AI coding agents (Claude, GLM, and similar) doing work in this
repository. It captures the project's architecture, conventions, workflows, and — most
importantly — the non-obvious gotchas that have already cost debugging time. Read it before
making changes.

## What This Project Is

MemberMocker generates realistic **fake** membership data (names, birthdays, phone numbers,
emails, real street addresses with coordinates) for organizations that need test data without
exposing real PII. Members are generated by a local LLM (Ollama running `llama3.1`) and
enriched with real addresses from OpenStreetMap data. The primary tested use case is Danish
cities, but most of the world works.

Users are **non-technical laymen**. Every user-facing string, error message, and form label
must be understandable without technical background. This is a hard requirement, not a
preference — see "UI/UX Conventions" below.

## Architecture

```
Browser ── React 19 + Vite + Tailwind (frontend/, port 5173 dev / 80 prod)
              │  axios, base URL from VITE_API_URL (dev) or /api via nginx (prod)
              ▼
FastAPI backend (backend/, port 8000)
              │  raw SQL via a thin psycopg3 wrapper (no ORM)
              ▼
PostgreSQL 17 (docker container, port 5432, bound to 127.0.0.1)

Backend also calls out to:
  - Ollama (env OLLAMA_HOST) — one chat call PER generated member, ~5–25s each
  - nominatim.openstreetmap.org — city bounding box lookup
  - files.openstreetdata.org — per-country address file download (tens of MB, per request)
```

### Key directories

```
backend/app/api/routes.py        All HTTP endpoints (members CRUD, custom fields CRUD, download)
backend/app/core/config.py      DB connection pool, schema creation, schema migrations
backend/app/models/              Pydantic models (member.py, custom_field.py)
backend/app/services/generator.py  Member generation: Ollama call + address sampling
backend/test_api.py              The entire test suite (pytest, runs against real Postgres)
backend/conftest.py              pytest options (--run-expensive) and markers
frontend/src/pages/DataSetPage.jsx   The single page; owns member list state
frontend/src/components/         MemberForm, MemberList, MapView, CustomFieldForm, CustomFieldList
frontend/src/services/api.jsx    All API calls + getApiErrorMessage() helper
Makefile                         Canonical entry points for tests and the database
```

## Running the Project

### Tests (start here — they are fast and safe)

```bash
make pytest                  # full suite, external APIs mocked, ~1–2s. Run this after ANY backend change.
make pytest-including-slow   # real Ollama + OpenStreetMap calls, ~2–3 min. Needs Ollama with llama3.1.
make db-up / make db-down    # start/stop the Postgres container
```

The Makefile automatically starts Postgres (docker compose dev file, `--wait` for healthy) and
runs tests against a **dedicated `membermocker_test` database** (created on demand). Tests
truncate all tables before each test — this is why they must never point at the real
`membermocker` database. The Makefile handles this; do not run bare `pytest` with production
env vars.

### Local development (preferred for agentic work)

```bash
# Terminal 1 — database
make db-up

# Terminal 2 — backend (auto-reloads on change)
cd backend && set -a && . ../.env && set +a && \
  DB_HOST=127.0.0.1 uv run uvicorn app.main:app --port 8000 --reload

# Terminal 3 — frontend (hot module reload)
cd frontend && VITE_API_URL=http://localhost:8000 npm run dev   # serves on :5173
```

Python dependencies are managed with **uv** (`uv add <pkg>`, `uv sync`) — never pip directly,
and never edit `uv.lock` by hand.

### Docker (production-like)

`docker compose up --build` (prod, frontend on :80) or
`docker compose -f docker-compose.dev.yml up --build` (dev, frontend on :5173).
Both compose files read `DB_PASSWORD` from `.env` with interpolation
(`${DB_PASSWORD:-postgres}`); keep the postgres service and the backend service using the
same variable — they drifted apart once and produced auth failures that only surfaced on
fresh volumes.

## Environment Gotchas (learned the hard way)

1. **Ollama binds to 127.0.0.1 on the dev machine.** Containers cannot reach it (no
   `host.docker.internal` mapping on Linux, and the bridge IP won't help against a loopback
   bind). If you need generation to work, run the backend *locally* with
   `OLLAMA_HOST=http://localhost:11434`, or override at invocation:
   `make pytest-including-slow OLLAMA_HOST=http://localhost:11434`.
   The `.env` value for `OLLAMA_HOST` may point at a LAN host that is not reachable — always
   verify with `curl $OLLAMA_HOST/api/tags` before debugging "generation is broken".

2. **`POSTGRES_PASSWORD` only applies on first volume initialization.** If auth fails, the
   volume was initialized with a different password than the current env. Fix
   non-destructively from inside the container (local socket auth is trusted):
   `docker compose -f docker-compose.dev.yml exec postgres psql -U postgres -c "ALTER USER postgres PASSWORD '<value-from-.env>'"`.

3. **Generation is slow by design.** One Ollama chat call per member (~5–25s each) plus a
   per-country address file download on every `/generate` request. When driving the UI or
   API, use `count: 1..3` and generous timeouts (≥120s). The first generate after a backend
   restart is slowest. `count` is capped at 100 per request by the `MemberConfig` model.

4. **Playwright for UI testing:** the Playwright MCP plugin requires branded Google Chrome at
   `/opt/google/chrome` (root install, may not be present). The reliable fallback is the
   Playwright npm library with cached headless Chromium: `npm install playwright` in a
   scratch directory and drive it with Node scripts (`ariaSnapshot()` for structure,
   screenshots for visual checks, `page.on('pageerror')`/`console` listeners for JS errors —
   always attach these listeners; they have caught real bugs here). Note that unhandled
   `alert()`/`confirm()` dialogs are auto-dismissed by Playwright — register a `dialog`
   handler or you will misdiagnose features as silently broken.

## Database Layer — How It Works and How Not to Break It

There is **no ORM**. `backend/app/core/config.py` exposes:

- A module-level `psycopg_pool.ConnectionPool` (min 1 / max 10), created lazily and
  thread-safely on first use. Table creation and schema migrations run once at pool creation.
- `get_db()` returns a `SimpleDB` wrapper that **borrows** a pooled connection.
- `SimpleDB.close()` returns the connection to the pool (after rollback of any uncommitted
  state). It does not close the underlying connection.

**Iron rule:** every `get_db()` call must be paired with `db.close()` in a `finally` block.
A leaked handle permanently removes a connection from a pool of 10; after ten leaks the app
deadlocks. This exact bug class existed twice (per-request connections that were never closed,
and `generator.py` skipping close). All current call sites follow the
`db = get_db(); try: ...; finally: db.close()` pattern — copy it.

### Schema and migrations

Schema is created with `CREATE TABLE IF NOT EXISTS` in `_initialize_tables()`. Schema
*changes* are handled in the same function with idempotent statements
(`ALTER TABLE ... ADD COLUMN IF NOT EXISTS`, conditional `UPDATE`s for data migrations, e.g.
legacy field-type renames). There is no migration framework; when you change schema, add an
idempotent migration statement there so existing volumes upgrade automatically on next start.

Tables:

- `members` — id (UUID PK), names, birthday, phone, email, address, latitude/longitude
- `custom_field_definitions` — id, name (UNIQUE), field_type, validation_rules (JSON as TEXT),
  created_at, **default_value** (applied to new members at generation time)
- `custom_field_values` — (member_id, field_id) PK, value TEXT, FKs with ON DELETE CASCADE

### psycopg3 pitfalls specific to this codebase

- **psycopg3 returns `json`/`jsonb` columns as already-parsed Python objects** (lists/dicts),
  not strings. Do not `json.loads()` them blindly. `custom_fields_from_json()` in `routes.py`
  handles both shapes — reuse it. (A helper that assumed strings silently turned every
  custom-field payload into `None` after the DuckDB→Postgres migration.)
- **`json_build_object(NULL, NULL)` raises an error** ("null value not allowed for object
  key"). Any `json_agg(json_build_object(...))` over a LEFT JOIN must carry
  `FILTER (WHERE <joined column> IS NOT NULL)`. Both member queries do this; keep it when
  copying them.
- **Pagination requires a deterministic ORDER BY.** `GET /members` orders by
  `(date_member_joined_group, id)` and takes `limit` (default/max 1000) and `offset` params.
  Never add an unordered LIMIT/OFFSET query.
- UUID columns come back as `uuid.UUID` objects; existing code defensively handles both UUID
  and string. Row access is positional (`row[0]`), so column order in SELECTs matters —
  `SELECT *` on `custom_field_definitions` is only safe because `default_value` was appended
  as the last column.

## Custom Fields — Domain Rules

Field types are **data types**, deliberately not semantic types:
`text`, `number`, `alphanumeric`, `date`, `datetime`. Legacy names (`string`, `integer`,
`email`, `phone`) are rejected on create and migrated in existing databases at startup. The
canonical list is `VALID_FIELD_TYPES` in `backend/app/models/custom_field.py` — routes import
it; never duplicate the list.

Default-value semantics (enforced by tests — keep them intact):

- Creating a field backfills **all existing members** with `default_value`, or a type-based
  fallback if none was given: `"0"` for number, today for date, now for datetime, `""` for
  text/alphanumeric.
- The default is stored on the definition, and **members generated later also receive it**
  (`generator.py` inserts `custom_field_values` rows for every definition). If a member had
  no value row for a field, the edit form would render no input for it and the field would
  become uneditable in the UI — that is why this invariant matters.
- Provided defaults are validated against the type with **layman-readable 422 messages**
  ("The default value must be a number"). Values are stored as TEXT regardless of type.
- Known gap (acceptable for now): editing a member's field *value* is not type-validated;
  only defaults are.

## Frontend Conventions

- **No `alert()` for errors.** Errors render inline in a red `role="alert"` box within the
  form that failed. Route every caught API error through `getApiErrorMessage(error, fallback)`
  from `services/api.jsx` — it unwraps FastAPI's `detail` (string or validation-error list)
  and has a dedicated message for an unreachable backend. `window.confirm()` is still used
  for destructive confirmation (delete member/field) and that is fine.
- **Every input needs a programmatically associated `<label htmlFor>`/`id`** (or
  `aria-label`). Placeholders are not labels.
- **Buttons reflect in-flight state**: disabled + present-progressive text
  ("Generating Members… (this can take a while)", "Saving…", "Creating Field…").
- Empty values display as italic gray *not set*, never as a bare `name:` with nothing after.
- After generation, `DataSetPage` refetches the member list rather than appending, so
  ordering always matches a page reload.
- Leaflet (`MapView.jsx`): the bounds API is `bounds.isValid()` — `isEmpty()` does not exist
  and fails silently as a page error, leaving the map at world zoom. `fitBounds` uses
  `maxZoom` + padding so a single marker doesn't over-zoom.
- Backend error `detail` strings are shown verbatim to end users. When writing a new
  `HTTPException`, phrase the detail as a complete, friendly sentence
  ('A field named "Points" already exists. Please choose a different name.').

## Testing Conventions

- The suite lives in `backend/test_api.py` and runs through FastAPI's `TestClient` against a
  real Postgres — there is no mocked DB layer. External services (Ollama chat, address
  lookup) are mocked by default via the `mock_chat` and `mock_addresses` fixtures; passing
  `--run-expensive` (what `make pytest-including-slow` does) disables the mocks.
- `pytest_addoption` only works in `conftest.py` — do not define it in test modules.
- When you add backend behavior, add a test in the same style: use the fixtures, hit the
  HTTP API (not internals), assert on JSON. Tests must pass with `make pytest` before you
  consider a change done.
- For UI changes, drive the real app with Playwright (see gotcha #4 above): check the aria
  snapshot, take a screenshot and actually look at it, and assert zero `pageerror`s. TESTING.md
  documents the human-facing testing workflow — update it if you change test entry points.

## Git / PR Workflow

- Branches are named `<issue-number>-<kebab-description>` (e.g.
  `7-use-postgresql-database-rather-than-duckdb`). PRs target `master`.
- Do not commit or push unless explicitly asked. Never commit `.env` (it holds the real DB
  password; `.env.example` is the template to keep in sync when adding variables).
- Keep `README.md`, `TESTING.md`, and this file in sync with behavior changes — the README
  lists the API endpoints and tech stack, TESTING.md the test workflow.

## Definition of Done for a Change Here

1. `make pytest` passes (19+ tests, currently ~1–2s).
2. If the change touches generation or external integrations: `make pytest-including-slow`
   passes (needs reachable Ollama — check first).
3. If the change touches the frontend: exercised in a real browser via Playwright with
   console/pageerror listeners attached, and screenshots visually inspected.
4. New user-facing strings are understandable by a non-technical person.
5. Docs updated where behavior changed.
